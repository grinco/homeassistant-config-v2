# Weather ahead: the tower picture on Home

*2026-11-11.*

## What it is for

One look at Home should say how to dress. The Weather section now sits at the top of Home, and
the stock `weather-forecast` card there (current conditions and the daily forecast) has a
picture of the Žižkov television tower as its background, in the weather of the **next three
hours**, by day or by night.

The card's own headline is still the weather **now** ("Cloudy"). Its second line, which
would otherwise repeat the location name, reads "Next 3 h: rain", so a rainy picture under a
"Cloudy" headline does not look like a mistake.

It is one card on purpose. A separate picture card above the forecast was tried first and
rejected by the operator: the tower is meant to be part of the weather card.

The picture shows the worst of the next three hours, not the current weather: if it is dry
now and rain arrives in two hours, the picture shows rain.

## Pieces

| piece | where | what |
|---|---|---|
| `weather_ahead` macro | `custom_templates/weather_ahead.jinja` | reduces an hourly forecast to the worst condition, its scene, day/night and the dressing numbers |
| `sensor.weather_ahead` | `configuration.yaml`, trigger-based `template:` | calls `weather.get_forecasts` (hourly) every 15 min, on start, on template reload and on a `weather.home` state change; state = the condition, attributes = the rest |
| scene images | `/config/www/zizkov/<scene>-<day\|night>.jpg` | 10 scenes × day/night, generated by `tools/weather-scenes/` |
| background | Home, the `weather-forecast` card in the Weather section | `card_mod` style: the scene image under a top and bottom scrim, white text, and the location line replaced by "Next 3 h: <condition>" |
| tests | `tests/weather/` | `run.py` checks the deployed macro, and `mutate.py` confirms the cases catch bugs; `test_card_style.py` checks the generated CSS offline (in CI) |

### Why a template sensor and not a native helper

No helper reads a forecast: since 2024.3 forecasts are only available through the
`weather.get_forecasts` action, and only a trigger-based template entity can call an action
and keep the response. That also rules out a UI template helper: the config flow has no field
for triggers, actions or attributes. The reduction is a macro rather than inline Jinja, so the
tests call the same code the sensor runs.

### The rules the macro implements

- **Window:** the hour in progress through the last hour that *starts* before now + 3 h. At
  10:30 that is 10:00–13:00. The 14:00 hour is out.
- **Worst condition:** what changes what you wear outranks what does not. From the top:
  thunderstorm, thunder, hail, pouring, snow, sleet, rain, wind, fog, cloudy, exceptional,
  partly cloudy, sunny/clear. On a tie the earlier hour wins.
- **Scene:** the 15 HA conditions map onto 10 pictures: sunny, partlycloudy, cloudy, rainy,
  pouring (also hail), storm (lightning, lightning-rainy), snowy, sleet (snowy-rainy), fog,
  windy (windy, windy-variant). clear-night is the sunny scene at night, and exceptional is
  cloudy.
- **Day or night:** `is_daytime` of the hour in progress, falling back to `sun.sun`.
- **Numbers, over the window only:** temperature min/max, feels-like minimum, precipitation
  sum, highest precipitation probability and highest wind speed.
- **No forecast** (integration down): the macro returns `{}` and the sensor goes
  unavailable. The card then shows the cloudy picture, day or night from `sun.sun`.

### Two traps in the sensor, both silent

Both left the sensor `unavailable` with nothing in the log:

- **A top-level `variables:` in a trigger template is rendered before `actions:` run.** At
  that point the forecast response `fc` does not exist yet. The reduction therefore runs in a
  `variables` step *inside* `actions`, after `weather.get_forecasts`.
- **A template result becomes a dict only if it reads as a Python literal.** The macro
  returns JSON, and JSON's `true`, `false` and `null` are not Python, so the variable stayed a
  string and `ahead.condition` was undefined. `| from_json` in the variable fixes it.

## The pictures, and how they move

They are drawn, not photographed. One public-domain photo of the tower against a clear
blue sky ([Wikimedia Commons, "Zizkov tv tower.jpg"](https://commons.wikimedia.org/wiki/File:Zizkov_tv_tower.jpg),
by Orange.man) is cut out of its sky, and `scenes.py` paints each scene around it: sky,
sun or moon and stars, clouds, rain, snow, a lightning bolt, wind streaks and fog. The tower
is relit for each scene, and at night the red obstruction light on the antenna is on.

Since 2026-11-12 the scene is animated (the operator asked for it), so each one is drawn as
layers rather than one picture:

| layer | element | motion |
|---|---|---|
| `<scene>-<dn>-back.jpg`: sky, sun/moon, stars, bolt | `ha-card` background | none |
| `<scene>-<dn>-clouds.webp`: a strip that wraps left to right | `ha-card::before`, 200 % wide | `transform` drift: 90 s per loop (partly cloudy), 30 s (windy), 160 s (overcast); storms also flash every 7 s |
| precipitation tiles `rain-light`, `rain-heavy`, `snow-near`, `snow-far`, `wind-day/night` | `ha-card::after` | `background-position`; rain falls on a 1:4 slant and snow sways, each loop an exact number of tiles, so there is no seam |
| scrim and `<scene>-<dn>-front.webp`: the tower, fog, obstruction light | `ha-card::after`, under the tiles | none |
| `glass-<kind>.webp`: drops and flakes landing on the screen | `ha-card::after`, topmost | a looping animated WebP (8 s); drops splat in, stick, then run down under gravity with a sideways wind drift and a thinning wet trail, and evaporate; flakes slide with the wind, melt into a drop and vanish |

The card's own content sits above all of it (`ha-card > * { z-index: 2 }`). Under
`prefers-reduced-motion` the CSS animations stop and the glass swaps to a still frame
(`glass-<kind>-still.png`); the scene still shows its weather, it just does not move.

`card_style.py` writes the whole `card_mod` style (one CSS block per scene, keyframes
included), so the CSS is generated, not hand-edited:

```bash
python3 tools/weather-scenes/cutout.py src.jpg tower.png 12   # 12 = how far the sky fill may grow
python3 tools/weather-scenes/scenes.py tower.png out/ 900x620 0.68 0.98   # size, tower centre, tower height
python3 tools/weather-scenes/glass.py out/                    # about 20 s
sudo install -m 644 out/* /usr/share/hassio/homeassistant/www/zizkov/anim/
python3 tools/weather-scenes/card_style.py 6 > style.jinja    # 6 = the ?v= cache-buster
```

After regenerating anything, bump the version: `/local/` is cached for 31 days. Then paste
the new `card_style.py` output into the card's `card_mod` style: the dashboard holds a copy,
not a reference.

`tests/weather/test_card_style.py` checks what makes the loops seamless and the layers line
up, without Home Assistant, so CI runs it:

- every rain layer moves on the 1:4 slant its tile is drawn with;
- every shift per loop is a whole number of tiles;
- each keyframe stop has one position per image layer;
- the reduced-motion override keeps the same layers.

Breaking any of the first three (or the override) turns it red.

**Open, not measured:** the falling tiles animate `background-position`, which the browser
repaints every frame. The clouds use a GPU-composited `transform` instead. On a phone or a
desktop this is smooth. On a low-power wall tablet it has not been measured. If it stutters
there, move each tile onto its own over-tall layer moved by `transform`, by whole tiles (the
seam rule carries over). The rule `ha-card > * { position: relative; z-index: 2 }` is blanket
on purpose. It lifts every piece of the card's content above the layers, and nothing inside
this card positions against the card itself.

## Not covered by a test

- That the sensor fires and the action returns a forecast: checked by reading
  `sensor.weather_ahead` back after deployment.
- That it moves: `render.py` freezes animations (`animations="disabled"`), so motion was
  checked by two shots 0.7 s apart in one browser session: about 6 % of the card's pixels
  change, and 0 % with reduced motion emulated.
- How the card looks: checked by rendering Home at 390 px and 1280 px with
  `tests/dashboards/render.py`. The scene images are 900×620 with the tower about two-thirds of
  the way across and slightly zoomed out (operator's choice, after a centred version), which
  suits the forecast card's shape. The text sits over the darker top and bottom of the
  picture.

`tests/weather/` runs only against the live instance: it reads the deployed macro, not the
repo copy, so the two can drift without the repo noticing. Copy the macro to
`/config/custom_templates/` and run `homeassistant.reload_custom_templates` before running
the tests. CI only compiles these files (`compileall`); it never runs them.

## Configuration as deployed

`configuration.yaml`:

```yaml
template:
  - triggers:
      - trigger: time_pattern
        minutes: "/15"
      - trigger: homeassistant
        event: start
      - trigger: event
        event_type: event_template_reloaded
      - trigger: state
        entity_id: weather.home
        to: ~
    actions:
      - action: weather.get_forecasts
        continue_on_error: true
        target:
          entity_id: weather.home
        data:
          type: hourly
        response_variable: fc
      - variables:
          ahead: >-
            {% from 'weather_ahead.jinja' import weather_ahead %}
            {% set rows = fc['weather.home'].forecast if fc is defined and fc is mapping and 'weather.home' in fc else [] %}
            {{ weather_ahead(rows, now()) | from_json }}
    sensor:
      - name: Weather ahead
        unique_id: weather_ahead_3h
        icon: mdi:weather-cloudy-clock
        availability: "{{ ahead.condition is defined }}"
        state: "{{ ahead.condition }}"
        attributes:
          scene: "{{ ahead.scene }}"
          daytime: "{{ ahead.daytime }}"
          temp_min: "{{ ahead.temp_min }}"
          temp_max: "{{ ahead.temp_max }}"
          feels_min: "{{ ahead.feels_min }}"
          precipitation: "{{ ahead.precip }}"
          precipitation_probability: "{{ ahead.precip_prob }}"
          wind_max: "{{ ahead.wind_max }}"
```

The weather card on Home:

```yaml
type: weather-forecast
entity: weather.home
forecast_type: daily
show_current: true
show_forecast: true
card_mod:
  style: |
    # the output of: python3 tools/weather-scenes/card_style.py 6
```

The style picks `scene` and `daytime` from `sensor.weather_ahead` (falling back to cloudy
and `sun.sun`), stacks the layers above for that scene, and replaces the location line
with "Next 3 h: <condition>".
