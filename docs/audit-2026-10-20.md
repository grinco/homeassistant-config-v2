# Repo audit — 2026-10-20

A scan of the committed config for privacy leaks, security surfaces, functional
discrepancies, and maintainability risks. This is a **reference audit of what is
committed**, not a re-review of the climate logic (that is covered by
`docs/climate-control-design.md` and the `tests/climate/` suite).

**Scope:** `automations/`, `esphome/`, `lovelace-dashboards/`, `tests/`, and the
docs they reference. The live instance (`.storage/`, `automations.yaml`,
`secrets.yaml`) is not in the repo and was not in scope.

**Method:** read each automation and dashboard export, the ESPHome configs, and
the test harnesses; grep for secrets, names, coordinates, and `person.*`
entities; verify the anonymisation claims against the committed files. The
local `tests/climate/rooms.local.json` (gitignored, holds the scrub terms) was
**not** present, so `tests/leakcheck.py` could not be run — its blind spots are
therefore part of this report.

**Severity scale.** HIGH = a real, actionable defect. MEDIUM = a defect or a
breach of the operator's own rule that needs a conscious decision. LOW = a
maintainability risk that is currently harmless. INFO = noise, no action.

## 1. Battery roll-up skips `volvo` by substring, not integration — MEDIUM

The "Any battery low" helper and the dashboard card that renders the list both
count every `device_class: battery` sensor under 15 %, except one matched by
entity-id substring:

```jinja
… | selectattr('attributes.device_class','eq','battery')
  | rejectattr('entity_id','search','volvo')
  | rejectattr('state','in',['unknown','unavailable'])
  | map('float',101) | select('lt',15) | list | count > 0
```

`docs/presence-lighting.md:166` documents that phones (`mobile_app`), the car
(`volvo`), and vacuums (`roborock`) are skipped *"by integration: they are
charged, not replaced."* Neither the helper (`resolved-sensors.json:100`) nor
the card (`home-view.json:120`) does that:

- They skip `volvo` by **entity-id substring**, not by integration.
- They do **not** skip `mobile_app` or `roborock`. Both publish
  `device_class: battery`, so the operator's phone and the vacuum are counted
  as "low" — contradicting the documented intent (a phone charged nightly is
  not a battery to replace).

The fix has to land in **two** places — the helper and the card carry the same
filter chain. The card also carries a hardcoded alias map from Zigbee IEEE
address to friendly name (`0x1035970000139e5b` → "IKEA BILRESA remote", …)
that silently degrades to raw names if a device is renamed.

**Simplification:** the documented design is already the single-source shape —
a *text* sensor that names every low battery (`none` when there is nothing to
say). One template sensor producing the list, the binary derived as
`count > 0`, the card just rendering the text. That kills the "change both
together or the card appears saying '0 low batteries'" warning in the
resolved-sensors note entirely, and the exclusion list lives in one place.

This is the same class of bug as the `\b`-vs-lookaround mistake in
`leakcheck.py` — a pattern that *looks* like it matches the intent but matches
the wrong thing.

## 2. The committed battery snapshot contradicts the test suite — MEDIUM

`tests/climate/cases.py:1450-1457` pins the battery threshold at **20 %**
("19 % is low", "exactly 20 % is not yet low") against the *live* expression —
`run.py` substitutes the running config, not a copy. The committed
`resolved-sensors.json:100` says **15 %**.

So either the committed snapshot is stale (live is 20, matching the doc and
the tests) or the suite is red. Given the doc, the tests, and the
2026-10-12 roll-up work in `presence-lighting.md` all say 20, the committed
export almost certainly predates that work. **Re-exporting
`resolved-sensors.json` (and the home view) is the fix** — and it would close
findings 1 and 3 at the same time if the live template already excludes by
integration.

## 3. Battery threshold: doc 20 %, committed template 15 % — LOW

The threshold lives in two committed places and they disagree:

- `docs/presence-lighting.md:166` — *"under 20 %"*, and the test suite agrees
  (finding 2).
- `resolved-sensors.json:100` — `select('lt', 15)`.

The dashboard card agrees with the helper at 15, so the doc (and the tests)
are the outlier against the committed snapshot — which is exactly what
finding 2 says: the snapshot is stale, not the doc. A re-export resolves this;
no live change is needed unless the live template also says 15.

## 4. "night" is duplicated in six places with no cross-check — LOW

The house's definition of night is hardcoded **byte-identically** in four
automations *and* two dashboard cards:

| file | line | context |
|---|---|---|
| `automations/climate-maintain-per-room-targets.json` | 24 | `night` |
| `automations/climate-radiators.json` | 10 | `night` |
| `automations/house-night-mode.json` | 69 | `sleep_on` |
| `automations/resolved-sensors.json` | 367 | `Lighting night` |
| `lovelace-dashboards/climate-view.json` | 58, 96 | two markdown cards |

```jinja
{{ a == 'armed_night' or (a in ['unavailable','unknown'] and is_state('schedule.climate_night','on')) }}
```

It is **consistent right now**, so this is not a bug. One correction to an
earlier draft of this audit: `tests/dashboards/lint.py` C22 does **not**
enforce a single definition of night — it only forbids the *pre-v5.12*
schedule-first pattern (`is_state('schedule.climate_night','on') or`). The
current alarm-first inline copies pass C22 while still being copies, and there
is no check across the automations at all. Given this repo's history — each
review round that "moved a hazard rather than closed it," each fix that
shipped the mirror of the bug it was fixing — a duplicated three-line
definition that can drift when someone edits one copy is exactly the shape of
hazard this project keeps paying for.

**Suggestion:** extract the definition to the one existing single source —
`binary_sensor.lighting_night` (`resolved-sensors.json:364`) — and have the
other copies read it, plus a test (in `tests/climate/` or a small lint)
asserting every consumer references that one helper rather than its own copy.
This is the structural version of the fix the `leakcheck.py` lookaround was.

## 5. Three referenced entities have no committed definition — LOW

These are referenced by committed files but defined in none of the committed
exports:

- `sensor.any_low_battery` — the doc's *text* roll-up ("names every battery
  sensor under 20 %, state `none` when there is nothing to say"); the export
  only has the *binary* "Any battery low". `automation.battery_watchdog`,
  which the doc says it feeds, is also doc-only.
- `sensor.any_safety_sensor_silent` — `home-view.json:74,79,178` render it
  ("a dead safety sensor is said"), but it is not in `resolved-sensors.json`.
- `sensor.lighting_left_on` — `house-away.json:85` and
  `house-everyone-left.json:39,208,222` read it; no committed definition.

A reader of the public reference cannot find out what these do. The export
looks like it predates the 2026-10-12 roll-up work; the re-export in finding 2
should pick these up.

## 6. "Žorik" vacuum name — INFO

`lovelace-dashboards/appliances-view.json:20,499` and
`docs/room-views-button-card.md:331` name the robot vacuum "Žorik"
(`vacuum.zorik`). It is an appliance, not a `person.*` entity, and "kid1" is a
role — so this is very likely fine. Verify against local memory that "Žorik"
isn't a child's name before it ships; it is a one-line check.

## 7. `mode: single` + 10-min trigger can drop a boot tick — INFO

`automations/climate-maintain-per-room-targets.json:798` runs the loop on a
10-minute pattern trigger plus state changes, with `mode: single` and
`max_exceeded: silent`. On boot, all five rooms re-evaluate through the full
sequence (per-room `wait_template` up to 10 s, preset re-reads, notifications,
breaker increments). If a run exceeds the 10-minute window, the next tick is
dropped silently. The `wait_template`s are bounded (10 s each, preset path
only, `continue_on_timeout`), so the worst case is limited — but worth knowing
the effective poll rate can drop on boot, and that `silent` hides it.

## 8. Three overload strategies, no rationale — INFO

- `house-alarm-sync.json:534` — `max: 25`, `max_exceeded: "warning"`
- `climate-maintain-per-room-targets.json:798` — `max_exceeded: "silent"`
- `house-everyone-left.json` / purifier — `mode: "restart"`

Not bugs, but the house uses three different strategies for overload with no
documented reason. A one-line note in `automations/README.md` would stop a
future reader from assuming they should all be the same.

## 9. Hardcoded device identifiers in the battery card — INFO

`home-view.json:120` keys its alias map on Zigbee IEEE addresses
(`0x1035970000139e5b`, `0x5c0272fffeac2293`, …). Not a privacy issue in a
family home, but they are another piece of live-instance fingerprinting in a
"sanitised" export — same category as the note that exports deliberately do
not match the live instance.

## What is fine (so this doesn't read as "everything is broken")

- **Anonymisation machinery** is sound: `leakcheck.py` uses lookarounds that
  exclude letters and digits (correct across `_`), scans committed blobs, and
  — importantly — does not print the matched term (the output can end up in a
  log).
- **`person.*` entities are clean.** Exactly three are committed:
  `person.vadim_grinco`, `person.janka_grinco`, `person.kid1_grinco`. There is
  no `person.kid2_*` anywhere in the committed files. The surname in
  `kid1_grinco` is an accepted risk (operator, 2026-10-20): the repo is public
  under the same surname, so the id reveals nothing the repo does not already
  show. One UX nit: the display name is "Kids room 1" — a room name on a
  person entity, which is confusing in the UI; a neutral person name would
  read better.
- **ESPHome OTA is passwordless on 3 of 4 devices, deliberately.** The three
  proxies inherit the passwordless `ota:` block from the included
  `esphome/bluetooth-proxies` package; only `hw-622.yaml` sets a password. The
  decision is already recorded in `esphome/secrets.yaml.example` ("Only
  hw-622 sets one"), so this is a documented choice, not an oversight.
- **The test suite** is the strongest part. `run.py` is a real decision oracle
  (substitutes impure reads with literals before evaluating), `wiring.py`
  closes the "names an entity that doesn't exist" gap, and `tests/dashboards/
  mutate.py` proves each lint check catches its target bug rather than passing
  for the wrong reason.
- **The alarm sync** correctly treats the physical panel as truth after a
  restart, and re-reads live state each run so its own echoes do nothing.
- **The purifier boot recovery** (recovering a run stranded by restart/reload)
  is sound, and `mode: restart` prevents runs from stacking.
- **`proposal-decide-act-split.md`** correctly deferred the custom-component
  rewrite to *after* presence detectors land, and is self-aware about its own
  contradictions.

## Recommended order

1. **Re-export** `resolved-sensors.json` and the home view (findings 2, 3, 5)
   — first check the *live* battery template: if it already excludes by
   integration at 20 %, the re-export closes findings 1–3 and 5 together.
2. If the live template still uses the `volvo` substring, fix it there
   (finding 1), ideally as the single text-sensor roll-up the doc describes.
3. (Optional) Refactor finding **4** to the single `lighting_night` source,
   with a cross-check test — the structural fix this repo keeps needing.
